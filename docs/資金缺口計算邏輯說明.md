# 資金缺口計算邏輯說明

> 本文件說明「資金預估週報」「銀行帳戶管理」如何算出**目前餘額、預計餘額、資金缺口**。
> 內容對照目前程式（`routes/cashGap.js`、`utils/settlementLookup.js`、`utils/bankAccountBalance.js`、
> `utils/financingProjection.js`、`utils/templateProjection.js`）撰寫，最後更新：2026-10。
> 舊版文件描述的「找不到帳戶結算時改用公司層級結算」**已移除**，見文末〈修訂紀錄〉。

---

## 1. 一句話總覽

```
目前餘額   = 最近一次結算的「實際餘額」 + 結算日起到今天的真實收支
預計餘額   = 最近一次結算的「實際餘額」 + 結算日起到檢查日的真實收支
             + 檢查日前的「借款預計還款」 + 檢查日前的「週期範本預計收支」
資金缺口   = max( 0 , 安全水位 − 預計餘額 )
```

每個**銀行帳戶**各算各的；全部帳戶的缺口再相加成「當日總缺口」。

### 計算流程

```
① 找起算點    → 該帳戶「最近一次結算」(日期 + 實際餘額)；沒有結算則期初 = 0、從頭算
② 交易歸戶    → 挑出屬於該帳戶、日期 ≥ 結算日 的真實收支（公司/帳戶名稱/帳號要對上）
③ 目前餘額    → 期初 + 日期 ≤ 今天 的收入 − 支出
④ 未來事件    → 日期 > 今天 的真實交易 + 借款預計還款 + 週期範本預計收支
⑤ 檢查日      → 每月 15 號、30 號（短月取月底）
⑥ 預計餘額    → 期初 + 到檢查日為止的所有事件
⑦ 資金缺口    → 預計餘額低於安全水位的差額
```

## 2. 步驟詳解

### 2.1 找起算點：最近一次結算

來源：「✅ 餘額結算」建立的記錄（`balance_settlements`）。

比對規則（`getLatestSettlement`，全站共用同一套）：

| 條件 | 規則 |
|---|---|
| 公司名稱 | 帳戶有公司時必須**完全相同** |
| 帳戶名稱 | 必須**完全相同** |
| 帳號 | 帳戶**有**帳號時，結算的帳號要相同，或結算沒填帳號（NULL，相容舊資料）；帳戶**沒有**帳號時不限制 |
| 取哪一筆 | 結算日期最晚的一筆；同一天有多筆時取較早建立（id 較小）的那筆 |
| 找不到 | 期初餘額 = 0，交易從 `2000-01-01`（即時餘額用 `1900-01-01`）起全部計入 |

**不會**退而使用「未指定帳戶的公司層級結算」。每個帳戶要有自己的結算，才會有正確的起算點。

> 結算日當天的交易**會被算進去**（條件是 `交易日期 >= 結算日期`），也就是把結算餘額視為「結算日當天開始時」的餘額。
> 結算日**之前**的交易不計入。

### 2.2 交易歸戶：哪些收支算在這個帳戶

資金預估週報（流水帳／帳戶卡片）採**嚴格比對**，三項都要對上：

| 項目 | 規則 |
|---|---|
| 公司名稱 | 交易的公司名稱 = 帳戶所屬公司名稱（帳戶沒有公司時 = 空字串）|
| 帳戶名稱 | 完全相同 |
| 帳號 | 帳戶**有**帳號 → 交易帳號必須相同；帳戶**沒有**帳號 → 交易帳號也必須是空值 |

因此每一筆交易只會歸到**一個**帳戶，不會重複計入。同公司若有「同名帳戶、不同帳號」，交易一定要帶對帳號，否則會漏算（不會重複算）。

> 由於是文字比對，**全形/半形、空格不同都會對不上**。建議一律用畫面下拉選單（含「貼上匯入」的帳戶下拉）選擇，不要手打。

### 2.3 目前餘額

```
目前餘額 = 期初 + Σ收入(結算日 ≤ 日期 ≤ 今天) − Σ支出(結算日 ≤ 日期 ≤ 今天)
```

「帳戶卡片」的總餘額、流水帳第一列「資金餘額」（今天）都是這個值。

### 2.4 未來事件（日期 > 今天）

三種來源，在預測中**一視同仁**地加減：

1. **真實的未來交易**：已經登記、日期在未來的收支記錄。
2. **借款預計還款**（`financingProjection.js`）
   - 條件：借款「啟用」、有設定「撥款/還款帳戶」、有「下次還款日」與「下次還款金額」。
   - 有「還款頻率」（每月／每季）：從下次還款日起，每 1 或 3 個月一期（月底日期自動夾到當月最後一天，例如 1/31 → 2/28）。下次還款日若已過，會往後跳到第一個 ≥ 今天的期數。
   - 無頻率（不重複）：只投影下次還款日那一筆；日期已過就不投影。
   - **不超過到期日**（有填到期日時）。
   - **累計投影金額不超過「目前本金餘額」**（見第 4 節）：下一期會讓累計超過就停止；本金已還清的借款完全不投影。這是把每期金額整筆當成本金的保守近似（實際還款通常含利息，真正能投影的期數可能更少）。
   - 只投影未來，**不會**回填歷史還款，避免跟日後實際登記的收支重複。
   - 顯示為「（預計）借款名稱 還款」，支出。
3. **週期範本預計收支**（`templateProjection.js`）
   - 條件：範本「啟用」、有「下次產生日」、金額 > 0、**沒有連結借款**（連結借款的範本不投影，因為借款本身已經投影同一筆還款）。
   - 頻率：每月／每季／每年；超過範本到期日的期數不投影；最多投影 60 期。
   - **已逾期未確認**（下次產生日 < 今天）的期數，全部**落在今天**，避免缺口被低估；說明會標示「（預計・已逾期未確認）」。
   - 歸戶規則：範本的公司名稱、帳戶名稱要與帳戶相同；帳戶有帳號時範本帳號要相同，帳戶沒有帳號時範本帳號也要是空值。
   - 範本金額是「預估值」，按「產生下一筆」並輸入實際金額後，範本的下次產生日往後推，該筆就變成真實交易，不會重複計算。

> 預計事件（借款、範本）**不會寫進收支記錄**，也不影響任何帳戶的即時餘額；它們只存在於預測畫面中。

### 2.5 檢查日

- 每個月的 **15 號與 30 號**；2 月等天數不足的月份，30 號改取該月最後一天。
- 只列出**今天（含）以後**的檢查日，從當月開始往後算。
- 帳戶卡片、對帳 API：往後 **3 個月**；資金流水帳：往後 **12 個月**。

### 2.6 預計餘額與資金缺口

```
預計餘額(檢查日) = 期初 + Σ收入(結算日 ≤ 日期 ≤ 檢查日) − Σ支出(同區間)
                   + 預計事件(日期 ≤ 檢查日)   ← 借款還款、週期範本
資金缺口(檢查日) = 預計餘額 < 安全水位 ? 安全水位 − 預計餘額 : 0
當日總缺口        = 所有帳戶在該檢查日的缺口加總
```

- **安全水位**是各銀行帳戶自己的設定（「🏦 銀行帳戶」維護），預設 0。
- 總缺口是各帳戶缺口**直接相加**：某帳戶盈餘**不會**抵銷另一個帳戶的缺口（帳戶之間不自動調撥）。
- 檢查日當天的交易**會算進**該檢查日的預計餘額（條件是 `日期 ≤ 檢查日`）。

## 3. 各畫面與 API 的差異對照

| 畫面 / API | 包含借款預計還款 | 包含週期範本預計 | 說明 |
|---|:-:|:-:|---|
| 資金預估週報 › **資金流水帳**（`/api/cash-gap-ledger`）| ✅ | ✅ | 往後 12 個月；逐筆事件 + 15/30 號結餘列 |
| 資金預估週報 › **帳戶卡片**（`/api/cash-gap-dashboard-by-dates`）| ✅ | ✅ | 往後 3 個月的檢查日表格與各日總缺口 |
| **對帳 API**（`/api/cash-gap-reconciliation`）| ❌ | ❌ | **只算真實交易**，用來和 Excel 逐項核對 |
| 簡易預測（`/api/cash-gap-dashboard`，目前前端未使用）| ❌ | ❌ | 預設 28 天，只算真實交易；缺口日期為估算值 |
| **銀行帳戶管理**的「即時餘額」| ❌ | ❌ | 只算到今天的真實交易，詳見第 5 節差異 |

### 資金流水帳專屬規則

- 第一列「資金餘額」= 今天的目前餘額；之後依日期逐筆列出未來事件（真實、借款預計、範本預計）並**逐筆累加**，遇到 15/30 號檢查日就插入一列該日餘額快照（黃底）。
- 範本逾期事件落在「今天」，會顯示在今天餘額列之後。
- 整段期間餘額一直是 0 的帳戶（沒有結算金額也沒有任何交易）會被隱藏。
- **可用資金** = 目前勾選且帳戶類型為「活存」或「定存」的帳戶，其**今天的目前餘額**加總（不含預計事件）。
- 同公司、同銀行有 2 筆以上「定存」時，畫面合併成一欄只顯示加總。
- **可用資金 − 目前貸款餘額**：≥ 0 藍底（足以償還），< 0 紅底並標示短少金額；貸款餘額是人工填寫的數字（`cash_gap_manual_loan_balance`），與借款管理的本金餘額無自動連動。

## 4. 借款的「目前本金餘額」

借款管理頁顯示的「目前本金餘額」與預測時投影還款的**上限**使用同一個定義：

| 模式 | 目前本金餘額 |
|---|---|
| 自動（預設，欄位留空）| 原始本金 − 全部還款記錄的本金合計 |
| 手動輸入 | 手動餘額 − **基準日之後**才登記的還款本金合計（基準日 = 輸入或修改餘額當天，台北時間；基準日當天及更早日期的還款視為已包含在手動餘額內）|

- 金額沒變、只改其他欄位時基準日不變；清空欄位回到自動模式。
- 投影還款的累計上限就是這個餘額；餘額 ≤ 0 即停止投影。

## 5. 已知差異與限制（對帳時請留意）

1. **「銀行帳戶管理」的即時餘額 與 週報的「目前餘額」可能不同**
   `utils/bankAccountBalance.js`（更新即時餘額）的交易比對比週報**寬鬆**：交易的公司名稱為空值也算、帳戶有帳號時交易帳號為空值也算、帳戶沒有帳號時不限制交易帳號。週報則是嚴格比對（第 2.2 節）。
   → 若有「公司或帳號欄位為空」的歷史交易，兩邊數字可能不一致。處理方式：補齊這些交易的公司／帳戶／帳號，再按「🔄 重新計算餘額」。
2. **「今天」的日期基準不同**
   即時餘額（`bankAccountBalance.js`）與簡易預測 API 用 UTC 日期當「今天」；流水帳、帳戶卡片、對帳 API 用**伺服器本機時區**的日期。台灣（UTC+8）每天 00:00～08:00 之間，前者會把「今天」視為昨天，因此當天日期的交易要到 08:00 之後才會進入即時餘額。
3. **預計還款把每期金額當成本金** 來比對上限，實際含利息時真正能投影的期數可能更少。
4. **貸款餘額（週報頁）是人工填寫**，不會自動等於借款管理各筆借款的本金餘額加總。
5. **補登日期早於結算日的交易**不會影響目前餘額（因為被視為已包含在結算金額內）；新增時系統會提示筆數。
6. **公司名稱、帳戶名稱、帳號是文字比對**：改名（例如在公司管理改公司名稱）後，既有交易與結算不會自動跟著改，會對不上。

## 6. 數字範例

設定：安全水位 **500,000**；今天 **2026-10-04**；最近結算 **2026-10-01、實際餘額 1,000,000**。

| 事件 | 日期 | 金額 | 來源 |
|---|---|---:|---|
| 支出 | 10-02 | −200,000 | 真實 |
| 收入 | 10-03 | +50,000 | 真實 |
| 支出 | 10-10 | −300,000 | 真實（未來）|
| 房租（每月 5 號，預估）| 10-05、11-05 | −80,000 | 週期範本預計 |
| 借款還款（每月 25 號）| 10-25、11-25 | −100,000 | 借款預計 |

**目前餘額** = 1,000,000 − 200,000 + 50,000 = **850,000**

| 檢查日 | 納入的事件 | 預計餘額 | 缺口（500,000 − 預計）|
|---|---|---:|---:|
| 10-15 | 10-02、10-03、10-10、10-05(房租) | 1,000,000 − 200,000 + 50,000 − 300,000 − 80,000 = **470,000** | **30,000** |
| 10-30 | 再加 10-25(借款) | 470,000 − 100,000 = **370,000** | **130,000** |
| 11-15 | 再加 11-05(房租) | 370,000 − 80,000 = **290,000** | **210,000** |

## 7. 數字與 Excel 不符時的檢查順序

1. **期初是否一致**：系統期初來自「結算」，不是 Excel。為每個帳戶各建一筆結算，實際餘額與 Excel 期初一致，且帳戶名稱／帳號選對。
2. **公司／帳戶／帳號是否完全一致**：交易、結算、銀行帳戶三者的文字要相同（含全形半形、空格）。同公司有同名帳戶時，每筆交易必須帶正確帳號。
3. **是否有空值欄位的交易**：公司或帳號為空的交易，週報不計入該帳戶（見 5-1）。
4. **日期**：交易日期是否早於結算日（不計入）；是否剛好在 00:00～08:00 之間檢查即時餘額（見 5-2）。
5. **預計事件**：Excel 若沒有借款還款或週期範本的預估，系統流水帳／卡片會比 Excel 多出這些預計列；用**對帳 API** 可以看到「只算真實交易」的數字：
   `GET /api/cash-gap-reconciliation?company=<公司名稱>&account=<帳戶名稱>`
   （回傳期初、結算日、各檢查日的收入合計／支出合計／預計餘額／缺口）
6. **重算餘額**：到「🏦 銀行帳戶」按「🔄 重新計算餘額」，再開週報比對。
7. **單一帳戶核對**：鎖定一個帳戶，手算「期初 + 該戶收支」對照畫面。

資料庫層級可檢查：`transactions`、`balance_settlements` 的 `company_name`／`account_name`／`account_number` 實際值是否與「公司管理」「銀行帳戶」一致。
